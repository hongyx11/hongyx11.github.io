OpenMP lets multiple CPU threads work on shared memory. It is approachable, but adding a pragma does not automatically make code correct or scalable.

## A parallel reduction

```cpp
double sum = 0.0;

#pragma omp parallel for reduction(+:sum)
for (std::size_t i = 0; i < values.size(); ++i) {
  sum += values[i];
}
```

Compile with OpenMP enabled:

```bash
g++ -O3 -fopenmp -std=c++20 sum.cpp -o sum
OMP_NUM_THREADS=4 ./sum
```

Without `reduction`, threads would update `sum` concurrently, causing a data race. A reduction gives each thread a private partial value and combines the partials safely.

## Work distribution

`schedule(static)` assigns predictable chunks with low overhead and works well when iterations cost roughly the same. `schedule(dynamic)` assigns chunks as threads finish and can help irregular workloads, but scheduling costs more.

Sparse rows may contain very different numbers of nonzeros, so loop iteration count alone does not describe work. Test schedules rather than assuming one is best.

## Scaling is not guaranteed

Strong scaling holds the total problem size fixed while increasing threads. Speedup is

$$S(p) = \frac{T(1)}{T(p)}.$$

Efficiency is $E(p)=S(p)/p$. Memory bandwidth, serial sections, synchronization, and load imbalance prevent perfect scaling. If one thread already saturates memory bandwidth, more threads may add little.

## Affinity and placement

Thread placement affects cache and memory locality. Record `OMP_NUM_THREADS`, `OMP_PLACES`, and `OMP_PROC_BIND` with results. On a multi-socket node, first-touch memory placement can also matter.
