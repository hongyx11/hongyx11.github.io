GPUs provide massive throughput by running many lightweight threads. A GPU is effective when a problem exposes abundant parallel work and memory accesses can be organized efficiently.

## Execution hierarchy

A CUDA kernel launches a grid of thread blocks. Threads within a block can cooperate through shared memory and block-level synchronization. Blocks must be independent because the runtime may execute them in any order.

```cpp
__global__ void saxpy(int n, float a, const float* x, float* y) {
  const int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) {
    y[i] = a * x[i] + y[i];
  }
}
```

A typical launch uses enough blocks to expose far more threads than the GPU can run at once:

```cpp
const int threads = 256;
const int blocks = (n + threads - 1) / threads;
saxpy<<<blocks, threads>>>(n, a, d_x, d_y);
```

Check launch and runtime errors. Synchronize before using a CPU timer or, preferably, use CUDA events for device execution time.

## Memory determines performance

Adjacent threads should usually access adjacent addresses so the GPU can coalesce requests. Reuse data from registers or shared memory when the reuse justifies the additional code and synchronization.

Host-to-device transfers cross a slower interconnect than on-device memory. Include transfer time when it is part of the application, but separate it from kernel time so the bottleneck is visible.

## Occupancy is not the goal

Occupancy describes active warps relative to hardware capacity. It helps hide latency, but maximum occupancy does not guarantee maximum performance. Register use, shared memory, instruction throughput, and memory access patterns also matter.

## Profile, do not guess

Use the tools available on your system to answer:

- Are transfers or kernels consuming time?
- Are global loads coalesced?
- Is achieved memory bandwidth reasonable?
- Is the kernel limited by memory, instructions, or dependencies?
